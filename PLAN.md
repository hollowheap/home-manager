### In-Progress

#### Dynamic Theming Injection, Asset Deduplication, & System Plumbing
- [ ] The dynamic theming pipeline, driven by Matugen and Wallust, is fundamentally clashing with Neovim due to NVF's strict read-only configuration directories. Because Nix locks the configuration inside the `/nix/store`, injecting a dynamically generated Lua color table at runtime triggers severe structural conflicts. The active task is to finalize a highly robust workaround utilizing `vim.fn.expand` or explicit cache path resolution within an isolated `luaConfigRC` block. This approach will allow Neovim to catch incoming `SIGUSR1` IPC signals and instantly hot-reload the impure cache files containing the dynamic highlights without requiring a full editor restart or violating Nix's build-time sandbox constraints.

- [ ] In parallel, the Mactahoe GTK theme requires urgent local disk optimization. Because the theme relies heavily on Sass compilation at build time, it creates massive disk cache bloat by generating duplicated SVG assets across its various color permutations. A custom post-build bash script utilizing `jdupes` must be finalized to scan the output directories, locate mathematically identical uncolored icons or shared index files, and seamlessly replace the duplicates with filesystem hardlinks to conserve inodes and reclaim storage space. Furthermore, the foundational plumbing module (`core-apps`), designed to standardize application launches across Hyprland, Niri, and MangoWC, remains unfinished. The module logic must be heavily refactored to pass application binaries as raw string types (`lib.types.str`) instead of strict Nix package derivations (`lib.types.package`). This ensures that path aliases and the required `uwsm app --` systemd execution scope commands launch correctly without native binary path resolution failures. This abstraction layer will also be expanded to systematically enforce VictorMono Nerd Font and Noto Sans CJK across all compositor environments while purging unnecessary default Linux fonts.

#### Hyprland Stability, Hyprglass Version Mismatch, & Session Shortcuts

- [ ] The display stack successfully utilizes the custom Noctalia greeter to launch native Wayland sessions via UWSM, but the active Hyprland configuration requires several urgent troubleshooting patches and plugin realignments. Primarily, the `hyprglass` plugin is currently failing to initialize due to a strict C++ ABI version mismatch rather than the previous Lua parse-time error. Hyprland plugins are notoriously volatile because they compile directly against the specific headers of the compositor; if the Nix flake input for the plugin does not perfectly align with the exact commit hash of the active Hyprland derivation, the compositor will inherently reject the shared object file (`.so`) to prevent system segmentation faults. To resolve this, the flake inputs must be strictly synchronized, overriding the plugin's Hyprland dependency pointer to perfectly match the host system's registry.

- [ ] Alongside this plugin compilation issue, a critical hardware-level crash persists where Hyprland freezes completely after the system returns from a suspended state. This requires an immediate patch in the root `configuration.nix` file to explicitly append `"nvidia.NVreg_PreserveVideoMemoryAllocations=1"` to the kernel boot parameters, physically forcing the proprietary Nvidia drivers to securely retain video memory allocations during ACPI sleep states. Furthermore, essential session keybindings must be finalized within the window manager's configuration tree to seamlessly tie the user ecosystem together. This includes defining a dedicated, `uwsm`-compatible desktop shortcut to summon the Noctalia clipboard history daemon reliably, ensuring clipboard persistence acts natively within the Wayland architecture. Finally, a fortified escape hatch must be built. A highly secure, dedicated shortcut must be bound in Hyprland to drop the user down to a fallback TTY rescue environment (e.g., executing `loginctl activate-session 2`), guaranteeing an immediate command-line recovery path if the graphical session completely crashes.

#### Secure AI Assistant Toolchain Migration
- [ ] The current Neovim artificial intelligence integration is heavily reliant on an unmaintained `gemini-cli` binary coupled with explicitly declared, raw API keys placed directly in the configuration. This fragile architecture was temporarily adopted due to a severe lack of native Asynchronous Context Processing (ACP) support in modern, lightweight terminal alternatives. However, this specific toolchain severely degrades standard editor responsiveness, introduces significant blocking latency during heavy buffer context ingestion, and presents a massive security vulnerability by leaving API tokens globally readable inside the `/nix/store`.

- [ ] To permanently stabilize the developer workflow, this entire AI toolchain requires a complete structural teardown and architectural migration. The primary conversational assistant must be securely migrated to `avante.nvim`, configuring the NVF module to utilize Claude 3.5 Sonnet (or OpenAI equivalents) as the primary backend processor. The goal is to aggressively leverage its superior side-by-side buffer diffing capabilities and whole-codebase context awareness entirely natively within the Neovim UI, fully eliminating the need for context-breaking terminal hops while actively writing code. To complement this, a secondary, highly lightweight autocomplete daemon must be deployed. By securely integrating `supermaven` (or `codeium`), the editor will be able to fetch predictive ghost-text streams asynchronously in the background, operating completely independently of the heavier Avante chat UI without saturating local GPU VRAM limits.

- [ ] Crucially, this new implementation must be securely routed to enforce declarative purity. The ecosystem must shift entirely towards OAuth-based browser tokens where the plugins natively support it, ensuring long-lived authentication occurs securely in the background. Where raw API keys are strictly unavoidable, they must be permanently stripped from the public dotfiles repository, injected into the established `sops-nix` vault, and exposed to the Neovim environment dynamically at runtime via secure, tightly scoped environment variables.

#### Sovereign Vaultwarden Mesh Network and WebAuthn PAM
- [ ] To achieve total credential sovereignty and eliminate reliance on third-party cloud infrastructure or fragmented command-line tools like `pass-store`, a self-hosted instance of Vaultwarden will be permanently deployed. This requires containerizing the Rust-based service natively via NixOS, establishing a localized and heavily encrypted database on the host hardware, and ensuring complete cross-platform synchronization API compatibility with all official Bitwarden mobile, web, and desktop applications.

- [ ] Because the system already utilizes DuckDNS via `ddclient` for dynamic IP resolution, the next architectural step is safely routing this external traffic without recklessly opening public router ports. A highly secure, cryptographic private mesh network (Tailnet) will be constructed to handle this. The system will deploy Headscale as the centralized control plane to authenticate roaming client devices securely, leveraging MagicDNS to map immutable internal hostnames to all connected nodes, thereby entirely obfuscating the sensitive Vaultwarden backend from public subnets and unauthorized scanners.

- [ ] To bridge the incoming DDNS domain to the secure mesh, a Caddy reverse proxy will be deployed directly in front of the local services. Caddy will be strictly configured to intercept incoming web traffic, terminate automatic Let's Encrypt SSL certificates to satisfy Bitwarden's strict HTTPS requirements, and seamlessly route approved traffic into the internal Vaultwarden port on `localhost:8080`. Once this backend is fully live and securely communicating across the Tailnet, the desktop ecosystem will be upgraded to utilize the KeePassXC browser extension. This extension will be explicitly configured to intercept all WebAuthn and passkey challenges, immediately triggering the local `hyprpolkitagent` to present a native graphical prompt that requires local PAM authentication (such as `fprintd` biometrics or a sudo password), effectively transforming the user's local machine into a physical hardware security module.
